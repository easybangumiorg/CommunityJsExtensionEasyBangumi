# 新源整理与管理方案

分析日期：2026-10-14。范围为本次提供的 22 条清单；站点首页探测发生于 2026-10-13，历史真机证据分别来自 10 月 9 日和 13 日。今天已连接小米 14 的无线 ADB，尚未把历史通过记录改写为今天的测试结果。本阶段整理方案与台账草案，不修改适配代码、索引或发布审批。

## 1. 先将三类身份分开

- **站点**：独立的内容服务，使用稳定 `siteId`。名称、域名、内容分类可以变化。
- **站点版本**：main / beta / next 等入口。相同品牌或主域名只能作为关系线索，不能直接证明接口、内容 ID 和登录会话兼容。
- **适配器**：客户端实际安装的 JS，身份是 `@key`。一个站点可能有多个历史实现；一份实现是否支持多个入口，需要显式记录和验收。

同一站点仅换域名且内容 ID、请求和解析契约兼容时，保留原 key，记录域名历史；任何字节更新都提升源版本并按最终 hash 重测。新版需要与旧版并存、请求契约不同或内容 ID 不兼容时，使用独立 key。现有 `heyanle.* / kazumi.* / jisoft.*` 不统一改名，防止影响用户已安装源和作品关联。新增 key 在实现时按仓库约定分配，本次不提前占用正式 key。

`dev/release` 是分发环境；`main/beta/next` 是网站版本；“有/无国漫”是有出处的内容标签。这三个维度相互独立。

## 3. 最小台账与权威来源

在官方源项目增加 `source-catalog.json`，手工维护两个集合即可；本次只保存设计草案，不让新字段参与打包。

| 集合 | 手工维护字段 |
| --- | --- |
| `sites` | `siteId`、名称/别名、经确认后才填写的 `familyId`、variant、当前入口、域名历史及关系证据、内容范围及出处、用户反馈与发生时间（未知则 null） |
| `adapters` | 已分配的稳定 `key`、绑定 siteId、明确支持的入口、dev 文件路径、维护人、工作状态、下一步、关联/替代关系及理由 |

尚无代码的候选只建 site 记录；不要造一个正式 key 或无效 JS 占位。无确证的 family/alias/replacement 关系保持空值。首次导入以 22 条用户原始信息为 intake，不能覆盖或遗漏其它现有源。

以下信息从现有文件读取，生成当前视图，避免多人重复手填：

| 信息 | 权威来源 |
| --- | --- |
| key、label、源版本、API、精确字节 hash | JS 头部及实际文件 |
| 真机验收历史和请求上下文 | `acceptance/evidence/` 原始 JSON |
| release 审批 | `release-manifest.json` |
| 已发布版本及字节 | 发布后核验的 `release-baseline.json` 与线上索引 |
| 当前清单、冲突、待办视图 | 上述数据生成的 Markdown/JSON；不是新的审批来源 |

状态至少分别展示 **用户反馈 / 机器验收 / 发布审批**。工作状态 `intake → investigating → implementing → ready_for_device → awaiting_review → maintained` 仅用于排期，不能代替验收或批准；`paused/retired` 需写明理由。

机器视图按 key/version/hash 取匹配原件，并显示实测日期、所测入口、设备/构建、证据时效和未解决反馈。“历史通过”“存在更新失败或反馈”“证据过期”分别展示，不能只取一个 PASS 字段。遇到新失败仍保留旧通过，不能跳过新失败挑旧成功。现有 7 天 gate 规则保持不变；日期过期不抹掉历史，也不自动下架已发布文件。

内容覆盖先保存原表分组及“未经核实”状态；稀饭 next、次元城、GGL beta、milimili、青空暂按原表前组理解，MiFun、路漫漫、嘶哩嘶哩、omootv、打驴按后组理解。原表排版有歧义，且内容会变动，应以站点实际栏目/作品核实，不能用这个标签决定仓库环境或准入。

## 4. 维护位置与同步

保留现有 84 个 dev 候选、18 个 release 文件和现有打包门禁，不为引入台账搬动全部目录。

1. 新开发和修复只以源仓库 `dev-extensions/` 为维护入口。
2. `extensions/` 是经过审核的精确版本快照；仍由 manifest/gate 控制分发，不在两份 JS 上平行修复。
3. Android `inner_source/` 是显式选择的调试/内置快照。后续提供 dry-run/diff 同步命令，记录源提交、key、版本、hash；不作为另一套开发主目录。
4. 首次同步先对齐差异，禁止覆盖未知修改。缺少 release 文件与“存在文件但字节不同”分别报告；相同 key/版本、不同字节必须处理冲突和版本升级。
5. 涉及正式 APK 内置源、版本与发布时，继续执行 Android 项目的 release skill；本次台账分析不触发发布。

可继续共用网络、URL、模型构造和验证桥工具，但站点首页/搜索/详情解析保留自己的契约。次元城、MiFun、路漫漫等旧模板缺 PageComponent，不能仅把所有站点塞进同一组 XPath 后批量宣称支持。

## 5. 分批执行

| 批次 | 内容 | 完成条件 |
| --- | --- | --- |
| A：台账与消歧 | 导入 22 条；补齐现有 key/域名；核实 MiFun、路漫漫、omootv、打驴；复测 7sefun、baimao 的冲突/迁移 | 每条都有明确的新增、修复、迁移或待核实任务；未知关系不强行合并 |
| B：首批新增与改版 | 建议先以 milimili、稀饭 next 作为新增调研对象；次元城作为现有源改版样本。GGL beta 单独排期 | 每批 2–3 个；先确认完整接口链及是否需要人工验证，再写实现和确定 key 策略 |
| C：已有源修复 | TvTFun、确认身份后的 MiFun/路漫漫、omofun03；旧 API 单独迁移 | 每项明确错误阶段；静态组件/API 合格，再使用最终字节真机测试 |
| D：回归与晋级 | 已实现且历史通过的源，及本批修复/新增项 | 首页→固定别名→第一部→逐线路首集→真实首帧及 ≥3 秒推进；验证交给用户，同请求重试；人工复核后 gate 才能晋级 |
| E：暂停/退役 | 长期不可用、确证关闭或不再维护的实现 | 保留 key、历史域名、原因和证据；实际分发下架单独审核索引差异 |

调研/静态检查可以并行；手机上的网页验证和播放器由一个执行者串行控制。当前无线目标 `10.135.231.77:41645` 已核对序列号 `6a022def`，但 IP/端口可能随网络和无线调试重启变化，执行前重新发现，不能把端点写成固定配置。

本次不增加新的测试算法：继续用已有源验收脚本和门禁。后续台账实现再补唯一 ID/key、有效引用、路径与 JS key 对齐、明确支持入口、同版本不同字节等校验；不把首页 HTTP 200 当作源可播。
